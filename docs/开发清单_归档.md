[改动 3.3] 内在奖励与反馈 (Intrinsic Reward & PE)

5. 学习引擎 Learning（先实现"能答题"，再谈"推理"）—— 已完成

这里拆成 A/B 两层，别一口吃成胖子。

5A. 序列记忆 + 模式抽取（最小可用）

 MemoryBank：存训练序列（token 序列）

 PatternMiner：

 抽取模板：如 a op b = c

 建立映射表：(a, op, b) -> c（先做加法）

 QueryEngine：

 输入 "1+3=?" → 查表输出 "4"（若已有）

 若无：返回 unknown/置信度低

验收： 喂 "1+1=2","1+2=3" 能正确回答训练集问题

5B. 规则发现与归纳（通过时空信号发现结构规律）

重要说明：
- 单从 1+1=2, 1+2=3 推不出 3=1+1+1
- 这不是类似 "++草=草+草=植物"，"++化=花+花=植物" 的字形比较
- 真正能发现的是：通过时空中的信号传播模式，归纳出结构性规律
- 类比：从"草"和"花"的共现模式中发现"艹"这个偏旁的结构意义
- 人类思考本质：通过时空中信号去发现规则、总结规律
- 推理时：根据已发现的规则去耦合组合

 RuleDiscovery：
 
 从时空传播模式中提取结构特征（而非简单的符号映射）
 
 识别共现模式、传播路径、激活序列
 
 归纳出可复用的结构规律（如：偏旁、运算符、后继关系）

 RuleStore：存储已发现的规律

 规律类型：结构规律（如偏旁）、运算规律（如加法）、后继规律

 RuleComposer：推理时根据已发现规则进行耦合

 输入问题 → 匹配适用规则 → 组合应用 → 输出结果

验收： 能从多个样本的时空传播模式中发现共性规律，并在新问题中应用这些规律

6. 演化系统 Evolution —— 已完成

目标：满足需求第2步：复制/遗传/变异/能量/熵增/吞噬

 Fitness 定义（先别玄学）：

 复制机制：

 if energy > threshold: reproduce()

 遗传：复制参数（传播阈值、移动倾向、初始统计先验）

 变异：扰动参数

 熵增/防膨胀：

 死亡与吞噬：

 附近 neuron 可拾取融合（能量 + 参数融合）

验收： 网络在持续输入事件时能稳定在一个规模区间，不会无限膨胀，且参数分布随时间变化

# 第五阶段开发清单：核心引擎重构与性能突破 (Phase 5)

> 历史快照说明：本文档用于保留 Phase 5 的阶段性规划与验收口径，不作为当前参数/版本真值来源；当前事实请以 README / parameters / architecture / metrics 为准。

## 1. 当前项目痛点分析

在完成前四个阶段的开发后（基础网络、进化算法、混合学习引擎、向量化加速），NeuroGenesis Lab 已经具备了完整的数字生命模拟能力。但随着实验规模的扩大，当前架构暴露出以下核心痛点：

1. **复杂逻辑的向量化瓶颈**：虽然 `vectorized.py` 使用 NumPy/SciPy 极大地提升了纯张量运算的速度，但进化算法（如尸体回收、局部突变）和符号规则发现（`learning.py` 中的 `PatternMiner`）包含大量复杂的条件分支，这些逻辑难以完全向量化，导致在 Python 层面产生严重的性能回退。
2. **GIL 限制与多核利用率低**：脉冲神经网络（SNN）的事件路由和神经元状态更新天然适合并行计算，但受限于 Python 的全局解释器锁（GIL），当前引擎无法真正利用多核 CPU，导致 10k+ 神经元规模下的 Tick 耗时显著增加。
3. **内存开销与 GC 抖动**：海量脉冲事件（Spike Events）和突触连接在 Python 中以对象或大矩阵形式存在，不仅内存占用极高，且频繁的创建和销毁会引发垃圾回收（GC）停顿，导致模拟帧率（Tick Rate）不稳定。
4. **高频观测的 I/O 阻塞**：虽然实现了 gzip 压缩和日志轮转，但在高频记录（`--log-interval` 较小）时，同步的磁盘 I/O 依然会阻塞主模拟循环。

---

## 2. 第五阶段核心目标

本阶段的核心目标是**引入 Rust + Python 混合架构**，在保持 Python 顶层 API 敏捷性的同时，彻底解决底层计算和并发瓶颈，使框架具备支撑 **100k+ 神经元** 实时模拟的能力。

- **目标 1**：引入 PyO3/Maturin 构建 Rust 扩展模块 `neurogenesis_core`。
- **目标 2**：将核心的事件路由、LIF 状态更新和基础进化逻辑下沉至 Rust。
- **目标 3**：实现真正的多线程 Tick 运算（基于 Rayon）。
- **目标 4**：优化 I/O 机制，实现异步无阻塞的观测数据落盘。

## 7. 风险预警

| 风险 | 影响 | 缓解措施 |
| ---- | ---- | -------- |
| VectorizedNetwork 多模型向量化引入分支过多，性能退化 | tick 耗时增加 | 使用 `model_type` 掩码分组计算，基准测试持续对比 |
| CLI 拆分导致导入路径变化 | 外部脚本/文档中的导入路径失效 | `__main__.py` 保留 fallback 导入兼容，废弃旧路径时发出 DeprecationWarning |
| mypy strict 模式暴露大量隐式类型问题 | 修复工作量超预期 | 分模块逐步启用，先完成 `protocols` / `config` / `encoding`，再推进核心模块 |
| 双引擎尸体回收/自适应机制对齐验证困难 | 统计对比结论不可靠 | 使用固定 seed + 500 ticks 长程运行，对比种群大小、能量均值、出生/死亡计数的时间序列趋势 |
| mkdocs 插件与 Python 3.14 兼容性 | 文档构建失败 | 文档构建 CI 固定使用 Python 3.12，仿真测试覆盖 3.10~3.14 |
| Codecov 令牌配置失败 | 覆盖率趋势无法跟踪 | 先使用 GitHub Actions Job Summary 内嵌报告作为备选 |
